# v0.6.87：短暂寻路后的恢复

v0.6.86半圈报告为37秒，基线为40秒。日志中的“寻路停稳”等待并非全部多余：末段持续无道路，不能为提速取消必要停车。几次中途短停后，光流仍显示约0.16–0.21m/s的前进，但恢复帧的逻辑PWM重新从 `(5,9)` 或 `(9,4)` 开始，实际峰值仅46。

根因是两种失路表示走了不同的加速状态处理：跟随命令为None时使用 `CommandRamp.pause()`，保留随时间衰减的恢复努力；寻路器明确返回零命令时却调用 `apply((0,0))`，把努力完全清零。零命令仍需实际发送，但不能仅据此认定车身已经静止。

修复后，仅在比赛任务允许寻路、寻路处于SETTLING且没有可用跟随命令时，将零输出作为暂停处理。可信光流确认仍在前进时按原速率衰减恢复努力；真正停稳、运动不可信、位移落在误差内或命令间隔达到300ms时仍清零。下一次有效巡线指令仍受原有平均／峰值努力爬升约束。寻路旋转脉冲、STOP、横道停留、完赛停车与故障处理保持独立；没有延长盲行或发送额外的前进命令。横道的寻路许可集中为一个方法，由应用协调和恢复处理共同读取。

另一处重复确认发生在严格有序端点接续已经成立，且当前选中路沿已独立通过多帧确认时。旧逻辑仍要求道路候选再确认一次，可能在旧支持到期前插入短停。现在直接采用这条实际观测的新路，丢弃旧尾段；没有接续几何证明、运动不可信、间隙过大、方向相反或几何冲突时仍走原确认流程。仅有车身余量推断、没有严格端点接续，也不能走这条快捷路径。

验证包括875项Python测试。新增测试覆盖实际零输出、滚动中的努力衰减与恢复、停稳／不可信运动／过期清零、独立路沿证据复用及断路／冲突反例。录制帧1452的道路接续保存在 `tests/fixtures/confirmed_handoff_20261110.json`，仅包含日志几何及来源，未声称重放原始图像。受控命令测试在 `(80,120)` 努力后暂停0.1秒且继续可信前进，随后0.1秒恢复巡线：旧处理会从峰值9开始，新处理能在原有努力增量预算内恢复到 `(80,120)`；这不是实车速度或圈速预测。

统一速度规划器仍为SHADOW观察器，本次实际改动位于既有道路接续和驾驶恢复逻辑，PWM上限、正常巡航参数、横道3.2秒停留、白线后40cm、发车灯许可与看门狗参数均未修改。控制台按钮和布局保持现状。v0.6.87尚需同赛段实测收益。
