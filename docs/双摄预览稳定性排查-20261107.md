# 双摄预览稳定性排查（2026-11-07）

本次设备版本：Maix 0.6.64，ESP32 0.4.2-self-recovery。UNO固件、接线与行驶参数未修改。所有测试保持小车停车，无实灯亮灭测试（用户目前没有灯）。

## 已确认的原因

1. 电脑网络切换。部署恢复时本机为10.73.124.39；出现“等待Maix状态恢复”时本机又变为192.168.3.187，目标10.73.124.209的路由经192.168.3.1。Maix网页、SSH和ESP32网页同时超时；用户确认是手动切网。不是自动回连故障，未修改电脑联网设置。
2. 预览与信号服务排队。在固定网络上，先采15次基线，再额外模拟4个ESP32读图客户端和3个Maix视频客户端，各接口再采35次。150次公开JSON请求全部成功，但ESP32响应最长796.3ms，JPEG最长825.4ms；Maix发车模块出现2/35次短暂不可用，而旧请求超时为300ms。旧固件将JPEG发送和发车请求放在同一个HTTP服务。根据[Espressif服务模型](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/protocols/esp_http_server.html)，同步处理函数会占用服务任务；此处存在排队争用。
3. 前端把状态未知判为离线。Maix轮询失败直接清空ESP32画面并标“离线”，无法区分电脑切网、Maix状态失败和ESP32图传失败。图片链路又只在load/error后取下一帧，缺少挂起请求的超时恢复。

## 设备侧证据

Maix应用PID在中断前后保持4079；检查时系统运行约13分钟，应用仍持续输出新帧；无线信号约−50dBm，可用内存约274MB。没有发现应用重启或内存耗尽证据。单个时间点的数据不能证明所有电源／无线工况均稳定。

基线：Maix状态中位28.3ms、最大101.3ms；ESP32状态中位36.3ms、最大68.6ms，均无掉线。以上压力为临时模拟，不代表正常运行时有多台ESP32或多次相机采集；各客户端读取同一JPEG缓存。

## 修复

- ESP32保留两个HTTP任务：80端口只服务页面、JPEG和公开状态；81端口服务发车状态与认证命令，独立队列和连接配额，控制任务优先级较高。取消原81端口阻塞式MJPEG，直接预览使用缓存JPEG短请求；限制预览连接并清理空闲连接。
- Maix发车请求使用81端口，保留300ms请求超时、750ms接收时效、400ms帧龄、2秒租约和事件期限。没有用放宽发车保护掩盖延迟。
- 页面分别显示“Maix连接中断”“信号状态未知”“预览重连”；Maix轮询失败时，已知地址的ESP32独立画面仍可刷新，锁定框不再沿用过期状态。
- 图片请求1500ms看门狗、250–2000ms退避重试、请求代号隔离迟到回调；后台标签页停止视频和状态请求，回到前台再连接。
- 将请求往返耗时计入控制状态年龄，过期控制保持禁用；STOP始终可用。
- 对超时或格式不合格的数据仍拒收，但保留成功解析的地址缓存；只有实际网络错误才重新解析，避免首次解析慢引发连续失败。增加请求耗时、控制端点和具体拒收原因用于后续定位；预览地址仍使用80端口。

## 验证

完整642项回归通过；其中真实页面JS覆盖7种断线、挂起、回调、后台恢复与时效场景。固件编译通过。

实机负载复测和会话认证结果保存在项目忽略目录`.maixpy/esp32-stability-20261107/`，以validation.json为准。

- 正常条件连续60次状态请求全部成功，发车模块0次掉线；最终0.6.64安装器已确认至少3个新鲜帧、未ARM和零输出；之后电脑再次回到192.168.3.187，最终跨网段复查未完成，不声称断网后的当前车端状态已验证。
- 额外4路ESP32图片、3路Maix视频的极限压力下仍出现1/35次短暂信号不可用，图片也有少量超时。未宣布无线抖动完全消失；保留严格发车保护，并让图传自行重连。测试客户端均已关闭。
- 基础链路短测：电脑到Maix为11/12包、最大约278ms；电脑到ESP32为12/12包、最大约40ms；Maix到ESP32为12/12包、最大约44ms。样本很短，不能推算长期丢包率；可确认无线层有偶发抖动。
- 会话认证、错误启动编号、重复ARM、取消、租约过期及旧会话拒收均实机通过；未向UNO发送行驶命令，未测试真实发车灯亮灭。
- 电脑本地8123服务在跳转模式下不再持续拉取ESP32图片；仅Wi-Fi设置期间短暂验证画面，原入口和设置页保留。
- 浏览器自动化接口持续超时，未取得新版界面截图；实际HTTP页面、两端状态和7种真实JS脚本行为均已验证。需刷新现有浏览器页面加载0.6.64。

正式的ESP32→UNO机内有线发车许可仍未实现；当前发车许可通过两块板之间的Wi-Fi，电脑不参与驾驶决策。

## 后续捕捉到的ESP32无响应

电脑重新连回正确网段后，Maix仍在线，但ESP32网络不可达，USB Q也无回应；只读ROM查询和硬复位后，ESP32立即以同一IP入网，Maix自动重新接收。能确认存在需要复位才能恢复的异常状态，但不能据此断言是相机、Wi-Fi驱动、供电或USB复位线中的哪一层。

新增恢复措施：主循环和相机任务分别注册8秒任务看门狗；相机连续3秒无新鲜帧会重启；配置过Wi-Fi且断线时每5秒尝试重新连接。设备状态增加重启原因、开机时长、可用堆内存、RSSI、重连次数及看门狗注册状态。新鲜启动编号继续让旧发车许可失效；未放宽发车条件。看门狗机制依据[ESP-IDF 4.4任务看门狗文档](https://docs.espressif.com/projects/esp-idf/en/v4.4.8/esp32s3/api-reference/system/wdts.html)。

内部卡住的直接原因尚未复现定位；自动恢复是保障措施，不能写成根因已经彻底消除。未人为制造死锁验证看门狗复位。

最终完成复查：Maix 0.6.64、ESP32 0.4.2-self-recovery。30次实机观察全部通信在线、保持单次启动、主循环／相机看门狗均已注册、新帧持续推进，观察窗口超过两个8秒看门狗周期；会话认证／取消／过期拒收再次通过，UNO零输出且无错误。两路JPEG实际返回960×240和320×240，新版HTML可访问。共642项回归通过。仍未进行真实信号灯亮灭或人为死锁测试，不能据此宣布无响应内部诱因已消除。最终记录在`.maixpy/esp32-recovery-20261107/validation.json`。
